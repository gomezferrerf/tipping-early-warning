# Design decisions

Short architecture decision records. Each entry states the context, the decision and its consequences.

## ADR 1: Euler–Maruyama for the stochastic integration

**Context.** The simulator must integrate $dx = f(x,r)\,dt + \sigma\,dW$ for hundreds of runs over thousands of time units, repeatedly, inside a sweep.

**Decision.** Use the Euler–Maruyama scheme with step $\Delta t = 0.01$, vectorised over runs, with increments $\sigma\sqrt{\Delta t}\,\eta$, $\eta \sim \mathcal N(0,1)$.

**Why.** The noise is additive, so the Milstein correction is zero and Euler–Maruyama already has strong order 1; a higher-order scheme would add code without adding accuracy. The step is much smaller than the relaxation times $1/\lvert\lambda\rvert$ of the stable branches, and the stored sampling interval (0.5) is a multiple of it (every 50th step). The scheme is a few lines of NumPy, easy to test against the exact OU statistics, and it vectorises across runs.

**Consequences.** The discretisation error can be checked against the analytical variance and AR(1) at fixed parameters, which the test suite does. Near the fold, where $\lvert\lambda\rvert \to 0$, the step is even more conservative relative to the dynamics, and the statistical error of the indicators dominates.

## ADR 2: Ornstein–Uhlenbeck linearisation as the theoretical baseline

**Context.** We need a prediction of how the indicators should move as $r$ approaches the fold, without simulating.

**Decision.** Linearise around the stable equilibrium and use the exact OU results: variance $\sigma^2/(2\lvert\lambda\rvert)$ and sampled autocorrelation $e^{\lambda\Delta t}$.

**Why.** The OU process is the one stochastic model with closed-form stationary variance and autocorrelation, and it is the standard theory behind critical slowing down. It makes the tests quantitative: simulation and theory must agree at small $\sigma$.

**Consequences.** The theory is the $\sigma \to 0$ limit and is not used as a predictor near the fold or at large noise, where nonlinearity and noise-induced escape matter. The documentation says so, and the simulation-to-theory ratio is reported instead of being assumed to be 1.

## ADR 3: Parquet for results, DuckDB for queries

**Context.** The sweep produces one row per (noise level, duration, seed) and is analysed in several ways: heatmaps, summaries, ad-hoc questions.

**Decision.** Write the tables as Parquet with a fixed schema and query them with DuckDB (SQL) or pandas.

**Why.** Parquet is typed, compressed and readable from any language; there is no schema drift between runs. DuckDB queries the file in place with no server, so documentation can show a reproducible SQL example. Both ship as ordinary wheels for Windows, Linux and macOS.

**Consequences.** Results are binary and are not committed (`results/` is ignored); they are regenerated by `tipping sweep`. Schema changes must be made deliberately, because figures and examples depend on the column names.

## ADR 4: uv for environments, just for task shortcuts

**Context.** The owner works on Windows; contributors may use Linux or macOS. The setup must work without `make`, bash-specific syntax or a manual Python install.

**Decision.** Manage the environment and the lock file with `uv`, and expose shortcuts in a `justfile` with a PowerShell shell on Windows.

**Why.** `uv sync` creates the environment, downloads the right Python and honours `uv.lock`, so CI and local runs use identical versions. Every `just` recipe is a plain `uv run ...` line, so the recipes behave the same on all platforms, and nothing depends on `just`: the README lists the underlying commands.

**Consequences.** `just` is optional. Recipes avoid shell features (pipes, globbing, `rm`); the `clean` recipe uses a short Python one-liner for portability.

## ADR 5: Figures take `--lang`

**Context.** The slide deck is in Spanish; the README and any international audience need English. A figure with baked-in text cannot serve both.

**Decision.** All figure and animation text lives in a per-language dictionary, and the commands take `--lang es|en`. The code that draws is language-independent.

**Why.** One code path guarantees that both versions show identical data and styling; only the strings differ. Text changes do not require touching plotting code, and a test can check that every key exists in both languages.

**Consequences.** New labels must be added for both languages. Figures are regenerated per language (`just figures` renders both); the deck uses Spanish, the README uses English.
